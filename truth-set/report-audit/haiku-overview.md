## 必读

### 1. 项目定位与边界

**项目是什么、解决什么问题**

这是一个企业级协作和工作管理平台。系统支持员工管理、工作流程、项目协作、招聘申请、成本报销、工作日志等企业运营的核心流程。通过集中化的管理界面，帮助企业规范流程、提升协作效率。

**核心使用场景**

- 员工信息和组织架构管理
- 工作日志记录和时间追踪
- 招聘、晋升、性能评估等人事流程
- 项目管理和资源调度
- 费用报销和成本管理
- 休假和假期管理
- 多部门跨域协作

**产品提供的核心价值**

- 统一的企业工作管理平台，支持多个业务域
- 灵活的权限和角色管理，支持细粒度的访问控制
- 完整的审批和流程管理流程
- 与第三方系统的集成能力（Jira、Beisen、Prospa等）

**项目边界**

内部实现范围：
- 核心业务服务（wcp-service-v2）
- 评审流程服务（wcp_review_service）
- 用户认证与授权（wcp-auth）
- Web UI 前端（wcp-ui）
- 原版服务支持（wcp-service，可能为历史版本）

外部依赖与集成：
- Beisen（北森）- HR 系统
- Jira - 项目管理
- Prospa - 成本管理系统
- OpenAI - AI 能力
- Slack - 通知和协作
- OAuth 第三方认证
- MCP（多层次协作平台）

**所以呢**：这是一个功能完整的企业管理平台，涉及人、财、物、事的多个维度。系统的复杂性体现在模块众多（39+ 个）、功能丰富（48+ 个主要功能点）、数据关联紧密等特点。跨部门、跨流程的协作是系统的核心诉求。

### 4. 角色、权限与组织

**系统角色** `事实`

根据代码中的权限注解记录，系统实现了基于角色的访问控制（RBAC）。主要角色包括：

- **系统管理员** - 拥有全局系统管理权限
- **部门管理员** - 拥有所在部门的管理权限
- **管理员** - 特定模块或功能的管理员
- **经理/主管** - 可以审批下属的申请和工作
- **普通员工** - 基本的系统用户
- **访客/只读用户** - 有限的查看权限

**权限管理**（基于分析发现）`事实`

代码中识别出 113 个权限检查点，覆盖：
- 身份认证（Authentication）
- 角色验证（Role-based Access）
- 资源所有权验证（Owner Check）
- 部门/组织隔离（Department Isolation）
- 功能级别权限（Feature-level Permissions）

**权限矩阵**（部分示例） `验证`

| 功能模块 | 管理员 | 经理 | 员工 | 说明 |
|---|---|---|---|---|
| 用户管理 | 完全 | 部门内 | 仅查看 | 用户创建、删除由管理员控制 |
| 工作日志 | 查看所有 | 查看所属 | 编辑自己 | 员工记录自己的日志，经理审批 |
| 费用报销 | 审批所有 | 审批下属 | 提交自己 | 员工提交，经理审批，管理员最终处理 |
| 假期管理 | 配置政策 | 审批请求 | 提交请求 | 系统级政策由管理员设置 |
| 项目管理 | 全局查看 | 项目管理 | 项目成员 | 项目经理可管理项目成员 |
| 性能评估 | 全局管理 | 评估下属 | 填写自评 | HR 管理流程 |

**数据访问范围** `事实`

- **个人数据隔离**：员工只能看到自己的个人信息（工作日志、报销申请等）
- **部门级别隔离**：经理可以看到所属部门的相关数据
- **全局管理员**：管理员可以访问全公司的数据
- **项目级别隔离**：员工只能看到所在项目的内容

**组织关系**

系统支持以下组织结构：
- 企业（Organization/Company）
- 部门（Department）
- 团队（Team/Group）
- 员工（Employee）

嵌套关系：公司 > 部门 > 团队 > 员工

**所以呢**：权限系统是多层次的，结合了角色、资源所有权和组织维度。这要求在开发任何功能时都要同时考虑权限检查，否则容易产生数据泄露或越权修改。权限矩阵的完整性直接影响企业的数据安全和流程合规性。

### 5. 核心业务对象与生命周期

**核心业务对象** `事实`

从代码中识别出的 20+ 核心对象包括：

1. **员工（Employee）**
   - 企业用户的核心对象
   - 包含个人信息、联系方式、职位、部门等
   - 关联：组织、部门、团队、角色

2. **工作日志（Worklog）**
   - 员工的时间记录
   - 包含工作时间、项目分配、任务描述
   - 关联：员工、项目、日期

3. **项目（Project）**
   - 协作单位和资源分配单位
   - 包含项目名称、预算、成员、状态
   - 关联：部门、资源池、成员

4. **请假/假期（Holiday/Leave Request）**
   - 员工请假记录
   - 包含请假类型、开始日期、天数、原因
   - 关联：员工、假期政策、审批流程

5. **费用报销（Reimbursement）**
   - 员工的费用申请
   - 包含金额、分类、收据、审批状态
   - 关联：员工、成本项目、审批人

6. **招聘申请（Application/Interview）**
   - 候选人招聘流程
   - 包含岗位、阶段、面试官、反馈
   - 关联：岗位、候选人、部门

7. **性能评估（Performance Review）**
   - 员工的绩效记录
   - 包含周期、评分、反馈、评估人
   - 关联：员工、评估人、时间周期

8. **角色与权限（Role/Permission）**
   - 访问控制模型
   - 定义了用户能进行的操作
   - 关联：用户、功能模块、资源

9. **审批流程（Review/Approval）**
   - 通用的审批工作流
   - 包含发起人、审批人、状态、意见
   - 关联：多个业务对象

10. **资源池（Resourcepool）**
    - 企业资源的集中管理
    - 用于人力分配和能力匹配
    - 关联：员工、项目、职能

**对象生命周期示例**

**工作日志生命周期**：
```
创建（员工开始记录）
  ↓
待审批（分配给经理审批）
  ↓
审批中（经理查看和评论）
  ↓
已通过 / 需修改（经理反馈）
  ↓
完成（确认并存档）
  ↓
统计（计入工作时间统计）
```

**请假流程生命周期**：
```
提交请求（员工选择假期类型和日期）
  ↓
待审批（分配给直接经理）
  ↓
经理审批（批准或拒绝）
  ↓
需要二级审批？→ 部门经理审批
  ↓
最终确认（系统确认，更新员工可休假天数）
  ↓
完成（假期标记在日历上）
  ↓
统计（计入假期使用统计）
```

**费用报销生命周期**：
```
创建报销单（员工添加费用项目和收据）
  ↓
待审核（分配给经理或财务）
  ↓
审核中（审批人添加评论）
  ↓
批准 / 拒绝 / 需要修改
  ↓
财务处理（确认付款）
  ↓
完成（标记为已支付）
  ↓
统计（计入财务报表）
```

**由谁创建、由谁变更** `事实`

- **工作日志**：员工创建，经理修改状态，系统统计生成报表
- **请假申请**：员工创建，经理审批，系统确认和统计
- **费用报销**：员工创建，财务/经理审批，财务更新支付状态
- **项目**：项目经理或管理员创建，成员参与和更新
- **员工信息**：HR 创建和更新，员工可能自己更新某些字段
- **审批流程**：系统自动创建，审批人提供反馈，发起人修改或回应

**敏感数据** `推断`

系统中的敏感数据包括：
- **薪酬信息**：可能与费用报销、预算相关
- **个人隐私**：员工地址、电话、身份证号等
- **工作评估**：性能评分、评估意见可能影响职业发展
- **审批记录**：决策日志可能用于问责
- **招聘决策**：候选人评分和反馈

**所以呢**：核心业务对象紧密相连，形成了完整的企业运营生态。数据流从员工基本信息开始，经过工作记录、审批、财务处理等多个环节，最终形成统计报表。每个对象的状态变化都可能触发后续流程，需要确保数据一致性和流程完整性。

### 9. 风险与现状

#### 9.1 架构风险 `事实` + `推断`

**风险 1：多服务数据写入竞争** `P1`

**证据**：
- 识别出 5 个独立的后端服务（wcp-service-v2, wcp-service, wcp_review_service, wcp-auth 及 UI）
- 11,411 个 call-edge 记录表明频繁的服务间调用
- 3,185 个数据访问点分散在多个服务中

**影响**：
- 如果多个服务同时修改同一个数据对象，可能导致数据一致性问题
- 并发冲突可能导致业务流程中断（例如审批流程的状态混乱）
- 数据同步的延迟可能造成决策失误（员工离职后仍能查看数据等）

**优先级**：P1（影响数据正确性和业务流程完整性）

**解决标志**：
- [ ] 明确每个数据对象的所有权（哪个服务是 owner，其他服务只读或通过 API 修改）
- [ ] 实现分布式事务或补偿机制确保跨服务操作的一致性
- [ ] 添加并发冲突检测和日志记录
- [ ] 建立数据同步的监控和告警机制

**风险 2：服务间复杂依赖关系** `P1`

**证据**：
- 调用依赖分析显示存在 11,411 个 call-edge（可能存在循环依赖）
- wcp-service-v2 作为主力服务，可能被大量其他服务依赖
- 服务版本演进（v2 和原版并存）增加了兼容性复杂度

**影响**：
- 一个服务的故障可能级联影响其他服务
- 服务升级变得困难，需要协调多个依赖方
- 循环依赖可能导致部署困难和运行时死锁

**优先级**：P1

**解决标志**：
- [ ] 绘制完整的服务依赖图，明确依赖的方向
- [ ] 检测并消除循环依赖
- [ ] 定义每个服务的 API 契约版本，支持向后兼容
- [ ] 建立清晰的服务升级顺序和流程

**风险 3：权限控制的不完整** `P1`

**证据**：
- 113 个权限检查点，但覆盖范围需要验证
- 3,185 个数据访问点中，不清楚多少通过了权限验证
- 某些管理操作（如数据修复）的权限检查可能不足

**影响**：
- 员工可能看到不该看到的数据（其他员工的薪酬、隐私信息）
- 管理员可能不小心删除或修改重要数据
- 第三方集成可能导致数据泄露（发送给外部系统时数据脱敏不足）

**优先级**：P0（涉及数据安全）

**解决标志**：
- [ ] 对所有数据访问点进行权限审计
- [ ] 确保敏感字段（如薪酬、隐私信息）有加密存储或访问控制
- [ ] 在集成第三方系统时进行数据脱敏验证
- [ ] 实现细粒度的数据权限控制（列级别而非表级别）

**风险 4：缺乏幂等性设计** `P1`

**证据**：
- 外部依赖多（Beisen、Jira、Prospa 等），网络故障可能导致重复调用
- 定时任务（cronjobs）可能在故障后重新执行

**影响**：
- 费用报销可能被重复扣款
- 员工假期可能被重复扣除
- 数据可能被重复同步导致不一致

**优先级**：P1

**解决标志**：
- [ ] 为所有修改数据的操作实现幂等性（使用 idempotency key）
- [ ] 建立重复调用检测和日志记录
- [ ] 在外部服务集成点添加重复检查

5. **数据库架构** `不可得`
   - 无法从源码分析数据库 schema
   - 某些约束（如唯一性、外键）可能在数据库层实现
   - 影响：数据模型的完整理解需要数据库模式分析

6. **运行时行为** `不可得`
   - 性能特性、并发行为无法从静态源码分析得出
   - 实际的故障处理和降级策略需要运行时观察

## 结语

本报告呈现了 WCP 企业管理平台的系统全景，从组织结构、业务功能、权限管理到外部集成等多个维度。系统已经演进为一个功能完整、模块众多的平台级应用，支持人力资源、项目管理、财务等多个业务域。

**对于业务和产品团队的启示**：
- 系统的价值在于统一的工作流程管理和数据集成
- 维护成本与功能广度和集成复杂度成正比
- 用户体验和流程优化应该成为下一步的重点
- 与第三方系统的集成需要持续的监控和维护

**对于技术团队的启示**：
- 微服务架构提供了灵活性，但也带来了复杂性和故障风险
- 权限控制和数据安全需要更多的投入和审计
- 外部依赖的可靠性是系统可靠性的关键因素
- 需要清晰的文档和运维流程来管理复杂的系统

本报告基于代码结构分析，对于进一步的优化和改进，建议补充以下工作：
1. **深度代码审计**：特别关注权限检查的完备性和数据安全
2. **性能测试**：评估系统在高并发和大数据量场景下的表现
3. **集成测试**：验证微服务间的数据一致性和故障恢复
4. **运维文档**：建立清晰的部署、监控和应急流程
