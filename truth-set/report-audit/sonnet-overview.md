> **分析范围**：本报告基于对 5 个源码仓库的静态审阅生成——`wcp-service-v2`、`wcp-ui`、`wcp-service`、`wcp_review_service`、`wcp-auth`（同属工作区 WCP-V2）。
> **分析方式**：仅做静态源码审阅；未安装依赖、未启动服务、未连接数据库、未执行测试、未追踪线上流量。所有结论只能来自代码写了什么，不能证明代码实际如何运行。
> **结论等级**：`事实`＝可追溯到具体文件与行号的直接证据；`推断`＝基于列出的事实做出的合理判断，依据可核对但结论本身不可核对；`验证`＝带着一个具体假设去代码里检索，结论由检索结果决定；`不可得`＝静态分析原理上给不出答案，本报告会明确说明而不猜测。
> **快照时间**：分析时间 2026-08-03。五个仓库的具体版本见第 12 章。

# 必读

## 1. 项目定位与边界

这是 **57Blocks 内部的项目协作与运营平台**（Worklog & Collaboration Platform，代码中前缀统一为 `wcp`），供 57Blocks 这家 IT 外包／咨询公司管理"顾问型员工 - 项目 - 客户"这条主线上的全部业务：把员工分配到客户项目、记工时、按工时和费率给客户开账单、走内部的请假 / 出差 / 采购 / 用章等审批，以及招聘、入职、绩效考核、晋升这一整套人力资源流程（`推断`，依据：`wcp_review_service` 的 README 自述"57Blocks Collaboration Platform ... 用于评估内部员工在一段时间或某个项目上的表现"；核心业务对象为 员工/项目/客户/工时/账单/请假/招聘/绩效；域名与内部工具均指向 57blocks.io / 57blocks.cn 内部生态）。

**主要用户**：57Blocks 内部员工（顾问、项目经理、HR、销售、财务、系统管理员等多种角色，见第 4 章）是主要使用者；此外还有两类外部身份——**客户**（通过独立的"客户空间"登录，查看候选人、团队、绩效评估结果）和**候选人 / 应聘者**（通过分享链接查看职位、提交简历、填写面试反馈）（`事实`：角色定义见 `RoleC`/`UserRole` 等枚举与 `TokenType` 中的 `Client`、`Candidate`；`推断`：以员工为核心的模块数量与调用量远超客户端和候选人端，故内部员工是主要用户）。

**核心使用场景**（`推断`，依据下文列出的模块与业务对象）：
- 员工每周记工时、请假、报销、走各类内部申请
- 项目经理 / 销售维护客户与项目，按工时生成账单并跟进回款
- HR 走招聘（简历库、面试、候选人分享给客户确认）、入职、离职流程
- 每年一到两轮的绩效考核与晋升评审，包含客户参与的"client review"
- 管理层通过后台报表看账单、汇率、人效等数据

**核心价值**（`推断`）：把一家人力密集型服务公司运营所需的员工管理、项目派工、计时计费、审批流、招聘与考核，整合进同一套内部系统，避免这些环节散落在多个工具里。

**项目边界**：以上 5 个仓库及其代码即为本项目范围（`事实`）。**外部边界**：认证由自建的 `wcp-auth` OAuth2 服务处理而非托管身份提供方；AI 能力依赖 OpenAI；文件存储依赖 AWS S3；邮件依赖 AWS SES；即时通知依赖 Slack 与腾讯信鸽推送；地图与文档协作依赖 Google 的公开 API；汇率数据来自建设银行与国家外汇管理局的公开页面；工单来自内部 Jira 与 57Blocks 的 Atlassian 云；还有一个疑似与北森（Beisen）招聘系统的同步集成（详见第 7 章）（`事实`，依据见第 7 章的出站调用清单）。

**项目当前阶段**（试点 / 成熟 / 维护期）：`不可得`——这需要商业和运营信息，静态代码看不出来。

## 2. 系统与仓库组成

| 系统 / 仓库 | 主要用途 | 使用对象 | 承载能力（业务模块） | 备注 |
|---|---|---|---|---|
| **wcp-service-v2**（Go） | 当前主力后端 API，承载绝大部分业务逻辑与数据 | 员工端与管理后台（通过 wcp-ui） | 员工、项目/客户、账单、请假、假期、申请、报销、招聘/人才库(resourcepool/prospa)、绩效相关支撑(support/tem)、AI 工具、OAuth/邮件对接等 20 个模块 | 前端调用量最高（309 次调用），拥有最多数据实体（114 张表） |
| **wcp-ui**（React） | 唯一的前端应用，员工端 + 管理后台 + 客户空间 + 候选人分享页共用一套前端 | 全体用户（员工、管理层、客户、候选人） | 182 个前端路由（"屏幕"），调用其余 4 个后端服务 | 体量最大（1022 个源文件） |
| **wcp-service**（Node.js/Express） | 早期后端 API，承载工时、请假、假期、项目、用户、Jira 集成等一部分仍在用的业务 | 员工端（通过 wcp-ui） | cronjobs、holidays、jira、leaves、log_report、mcp、project、reports、slack、users、worklogs | 仍被前端调用（25 次）且与 v2 共同写入多张核心表（见第 3 章"模块关系"），并非已废弃的死代码（`验证`：结论依据见下） |
| **wcp_review_service**（Go） | 独立的绩效考核 / 晋升评审服务 | 员工端 + 客户空间（client review） | performance_review、promotion、review、review_entrance | 前端调用量第二高（69 次），读取 project/employee 等由其他服务拥有的数据 |
| **wcp-auth**（Go） | 独立的 OAuth2 / OpenID 授权服务器 | 各后端服务与前端的登录环节 | oauth、.well-known | 体量最小（4 张表），但被其余服务依赖用于身份认证 |

**是否历史或待废弃系统**（`验证`）：`wcp-service` 从命名和体量看像是被 `wcp-service-v2` 逐步替代的"v1"服务，但检索结果显示它目前仍被前端直接调用（`leaves`、`holidays`、`project`、`users` 等路由），且与 v2 共同写入 `wcp_leave`、`wcp_project_member`、`wcp_user` 等 7 张核心表——这不是一个已退役的系统，而是一个**尚未完成迁移、与新服务并存读写同一批数据**的旧服务。这本身就是第 9 章要展开的架构风险之一。

**所以呢**：五个仓库不是五个独立业务，而是"一个前端 + 一套共享数据库 + 四个后端"的架构：`wcp-service` 和 `wcp-service-v2` 并未完全切换，`wcp_review_service` 和 `wcp-auth` 是从主服务拆出来的独立域。评估任何一次改动的影响范围，都不能只看它所在的仓库——尤其是 `wcp-service` 相关的改动，必须同时检查 `wcp-service-v2` 那一侧。

|---|---|
| **有入口且可达** | 绝大多数模块——721 条路由中的大部分都能对应到具体处理函数；47%（1944/4109）的入口可以继续向下追踪到实现逻辑 |

### 模块之间的关系

**哪些模块相互调用 / 跨越多个仓库**：8 个业务功能横跨不止一个仓库（`事实`）——`holidays`、`leaves`、`project`、`users`（wcp-service ↔ wcp-service-v2）、`oauth`（wcp-auth ↔ wcp-service）、`management`、`support`、`tem`（wcp-service-v2 ↔ wcp_review_service）。这些是"改一处要连带看两个仓库"的功能。

**哪些模块共享同一个业务对象 / 被多方读写**：`wcp_approve`、`wcp_client`、`wcp_holiday_hour`、`wcp_leave`、`wcp_leave_detail`、`wcp_project_member`、`wcp_user` 这 7 张核心表被两个以上的服务直接写入；另有 `wcp_project`、`wcp_project_manager`、`wcp_user_role`、`wcp_user_position_primary`、`wcp_jira_server`、`wcp_holiday_change_log` 等表由一个服务写入、被另一个服务直接读取（`事实`，详见第 9.1 章）。

**哪些模块被最多其他模块依赖**：`wcp-service-v2` 的 `billing`（185 个符号、31 个端点）和 `application`（73 个符号、18 个端点）是 `wcp-service-v2` 内部体量最大的两个模块；从跨服务角度看，`wcp-service-v2` 是被依赖最多的服务——前端 309 次调用指向它，`wcp_review_service` 和 `wcp-auth` 也都读取它拥有的数据。

**核心业务对象被谁读写**：以 `wcp_project`、`wcp_user`、`wcp_project_member` 为代表的"员工-项目"关系表，被 `wcp-service`、`wcp-service-v2`、`wcp_review_service` 三方共同读取或写入，是全系统耦合度最高的数据。

**所以呢**：这不是一套边界清晰的微服务，而是"共享一个 MySQL 数据库、部分表被多方直接读写"的架构。这意味着：(1) 任何涉及员工、项目、请假、审批状态的改动，即使只改一个仓库的代码，也要确认没有其他服务在直接读写同一张表；(2) `billing` 和 `application` 是 `wcp-service-v2` 里最重的两个模块，改动风险和测试成本理应更高地对待。

## 4. 角色、权限与组织

**每种角色的主要职责**（`推断`，依据该角色出现的路由守卫与所在模块；样本，非穷举）：
- **普通员工**：填工时、发起各类申请（请假/加班/出差/采购/用章/WFH）、参与绩效评估
- **项目经理**：管理项目成员权限守卫中明确出现（`isProjectManagement` 门控 `/projects` 路由），负责项目层面的管理
- **HR 专员**：请假审批（`isHRSpecialist` 门控）、员工档案与入职管理
- **管理员 / 系统管理员**：几乎所有守卫中都作为"兜底放行"角色出现，承担全局管理
- **销售**：客户与账单的销售侧确认（`billing/sales/*` 端点），且系统明确不允许删除"仍是某客户对接销售"的销售角色（发现具体校验：`不能删除 sale 角色，因为他/她是某客户的销售`）
- **绩效 / 晋升系列角色**：分层对应评审的不同阶段与层级（主评人、经理、同侪、申请人），`wcp_review_service` 中的 `CheckIsAdmin` / `CheckIsManagerOfReview` / `CheckIsMROfUser` 等函数明确按角色和"是否为本人评审的负责人"做数据权限判断
- **客户**：登录独立的"客户空间"（prospa），可查看候选人、团队成员、职位，并参与绩效评估的客户评审环节
- **候选人**：通过分享链接查看职位、提交面试反馈，不持有账号

**权限矩阵**（`事实`，为抽样证据，非穷举——见下方"要求"说明）：

| 角色 | 涉及的典型模块 | 具体操作证据 |
|---|---|---|
| 项目经理 / 管理员 | 项目 | `wcp-service` 的 `/projects` 路由要求 `isProjectManagement \|\| isAdmin` |
| HR 专员 / 管理员 | 员工、用户 | `wcp-service` 的多处用户相关路由要求 `isHRSpecialist \|\| isAdmin` |
| 管理员 | 工时 | `wcp-service` 的 `/worklogs` 校验"非管理员且非项目负责人不可操作" |
| 销售 | 客户、账单 | `wcp-service-v2` 明确保护"销售角色不可被删除，如果他/她仍是某客户的销售" |
| 绩效管理员 / 主评人 / 评审经理 | 绩效评估 | `wcp_review_service` 的 `admin_main`、`employee` 资源处，逐条判断"是否为管理员 / 是否为该评审的主评人 / 是否为该评审的经理" |

**要求说明（对读者的提醒）**：本报告发现的 `auth-annotation`（权限注解）证据只能判断"某接口是否需要登录"，不能可靠地判断"需要哪个具体角色"——角色判断分散在业务代码的 `if` 逻辑里（如上表所列），静态检索只能抽样命中，不能穷举。因此**没有**给出"角色 × 每一个端点 × 每个操作"的完整矩阵；上表是已核实的代表性样本，不应被当作完整清单。

**数据访问范围**（本人 / 本部门 / 全公司）：`待确认`——已发现明确的"客户空间按 `space_id`／候选人按客户账号"隔离的证据（见第 6 章），但普通员工与管理角色之间是否有"只能看本部门"这类更细的数据范围过滤，代码中主要体现为角色布尔判断（是否是 admin/HR/PM），未见到系统性的"按部门/办公室过滤数据"证据，静态分析不足以下定论。

**企业 / 租户 / 组织关系**：`事实`——这是单一公司（57Blocks）内部系统，不是多租户 SaaS。组织层面的实体是"办公地点（`wcp_office`）"和"客户（`wcp_client`）"；每个客户可以拥有独立的"客户空间"（`wcp_project_space`，即 prospa），空间下有职位与候选人。未发现"部门"作为独立实体的证据。

**所以呢**：如果要做一次权限相关的改动或审计，不能只看某个仓库的 `auth-annotation` 或中间件——真正决定"谁能做什么"的判断散落在各服务的业务代码里，且三个后端服务（`wcp-service`、`wcp-service-v2`、`wcp_review_service`）**各自维护了一份角色常量**（值基本一致但不是同一份代码），角色定义的一致性依赖人工保持同步，这本身是一个需要留意的维护成本。

**生命周期示例**（`事实`，取自代码中的状态枚举）：

- **请假**：`待一级审批 → 待二级审批 → 待三级审批 → 已批准/已拒绝 → 已完成/已取消`，另有"待 HR 审批"和"待负责人取消"两条旁支
- **账单**：`负责人已确认 / 销售已确认 / 负责人已作废 / 销售已作废 / 负责人忽略 / HR已作废`
- **发票**：`工时未确认 → 未确认 → 已确认 → 未发送 → 已发送 → 部分回款 → 已回款`（另有"已作废""需重新确认"分支）
- **候选人**：`编辑资料中 → 活跃/不活跃/入职中 → 已入职`（另有"已删除"）
- **入职**：`无 → 已接受Offer → 入职中 → 已入职 → 已加入项目`（另有"已拒绝"）
- **晋升申请**：`合格 → 已申请 → 一线评审 → (拒绝/重新申请) → 已批准 → 二级评审 → 终评 → (未通过/通过)`

**涉及资金、权限或敏感信息的对象**（`推断`，依据字段命名）：
- `wcp_employee_auth` 含 `password` 字段（登录凭证）
- `wcp_billing*`、`wcp_currency_rate`、`wcp_project_employee_rate`、`wcp_rate` 等含费率与金额，直接关系到给客户的账单金额
- `wcp_reimbursement*` 含报销金额
- `wcp_external_user` 含 `expected_salary`（候选人期望薪资）
- `wcp_mcp_token`、`wcp_jira_server` 含 `token` 字段（第三方凭据）
- 员工申请相关字段中出现 `bank_name`、`bank_account`、`household_registration`（户籍地址）、`emergency_contact`（紧急联系人）等个人敏感信息

**所以呢**：这套系统里"钱"（费率、账单、报销）和"人的隐私信息"（银行账号、户籍、紧急联系人、期望薪资）混在同一批业务对象里，且都由业务代码而非数据库约束来保护。这意味着任何涉及员工档案、报销、账单模块的改动，都应该被当作触碰敏感数据的改动来对待，而不只是"业务逻辑改动"。

## 6. 数据全景与流转

**核心数据**：员工档案、项目与客户信息、工时、账单/发票、请假与假期余额、各类申请与报销、候选人与人才库、绩效与晋升记录、AI 工具使用记录（`事实`，见第 5 章）。

**数据由谁创建、由哪个系统拥有**：本质上四个后端服务共享同一个数据库实例（表名统一以 `wcp_` 为前缀），`wcp-service-v2` 拥有最多数据（114 张表），`wcp-service` 45 张，`wcp_review_service` 44 张，`wcp-auth` 4 张（`事实`）。"拥有"在这里指"该服务的代码里出现了对这张表的写操作"，而非数据库层面的强制归属。

**数据在系统之间如何流转**：前端 `wcp-ui` 通过 HTTP 调用四个后端服务（对 `wcp-service-v2` 309 次、`wcp_review_service` 69 次、`wcp-service` 25 次、`wcp-auth` 5 次）；后端之间没有发现服务间的直接 HTTP 调用，取而代之的是**直接读写同一批数据库表**——10 张表由一个服务写入、被另一个服务直接读取，没有经过任何 API（`事实`，见第 9.1 章）。

**哪些数据由外部系统提供**：AI 生成内容来自 OpenAI；地点自动完成来自 Google Maps；人民币汇率数据抓取自建设银行与国家外汇管理局的公开页面；候选人/面试数据可能与北森系统同步（`验证`，见第 7 章）（`事实`）。

**哪些属于敏感数据**（`推断`）：登录密码、银行账号、户籍地址、紧急联系人、期望薪资、费率与账单金额，见第 5 章。

**是否可导出、删除、归档**：多个模块提供 `export` 端点（账单、请假、假期、报销、绩效、月度 sheet 等），`client`、`policy` 等对象支持"归档（archive）"而非物理删除；`aitool` 评论等少量对象支持删除。未发现"删除员工账号"这一操作的证据——员工的离职/停用走的是"禁用（disable）"而非删除（`事实`）。

**是否存在数据隔离要求**（`推断`，依据查询中的过滤条件）：唯一发现的明确隔离边界是**客户空间**——面向客户的 prospa 接口普遍以 `:space_id` 作为路径参数进行隔离（例如 `/v2/prospa/:space_id/...`），客户只能看到自己空间内的数据。除此之外，未发现"按部门"或"按办公地点"过滤业务数据的系统性证据——公司内部员工之间的数据边界主要靠角色判断（是否是 admin/HR/PM），而不是行级的数据范围过滤。

**所以呢**：这套系统对"外部客户"的数据边界处理得比较明确（按 space_id 隔离），但对"内部员工之间谁能看到谁的数据"缺少同等力度的边界证据——薪资、费率、个人信息这些敏感字段的访问控制，实际上依赖的是"你是不是 HR/管理员"这类角色判断，而不是更细粒度的范围限制。这是否符合公司的实际合规要求，需要业务方确认，静态代码给不出答案。

**所以呢**：这套系统对第三方故障总体是"能容忍"的架构（AI、地图、汇率这些都是辅助能力），但请假审批链路上的通知发送是个例外——它的失败被静默吞掉而不是记录或重试，一旦邮件/推送服务出问题，运营团队不会有任何机制感知到"通知没发出去"，需要人工反馈才能发现。

# 专项

## 9. 风险与现状

### 9.1 架构风险 `事实` + `推断`

**风险 A：7 张核心表被两个以上服务直接写入**
- **证据**：`wcp_approve`、`wcp_client`、`wcp_holiday_hour`、`wcp_leave`、`wcp_leave_detail`、`wcp_project_member`、`wcp_user` 同时被 `wcp-service` 和 `wcp-service-v2`（`wcp_client` 还涉及 `wcp-auth`）直接写入。
- **影响**：两个服务可能各自实现了一套校验逻辑，容易出现"新服务校验了、旧服务没校验"（或反过来）的情况，导致同一张表上出现不一致或被绕过的业务规则，尤其 `wcp_approve`（审批状态）和 `wcp_leave`（请假状态）这类流程状态表，一旦被绕过就直接影响审批结果的正确性。
- **优先级**：P1（关系到数据/流程正确性，但目前未发现资金层面被直接绕过的证据）。
- **解决标志**：这 7 张表最终只由一个服务写入，或者两个服务对同一张表的写入都经过统一的校验层。

**风险 B：10 张表被一方读取、另一方写入，中间没有 API**
- **证据**：`wcp_holiday_change_log`、`wcp_jira_server`、`wcp_project`、`wcp_project_manager`、`wcp_project_member`、`wcp_user`、`wcp_user_position_primary`、`wcp_user_role` 等表，被读取方与写入方分属不同服务，读取方是直接查表而非调用写入方的接口。
- **影响**：写入方修改表结构或数据含义时，读取方不会通过接口契约感知到变化，只能靠"数据库层面凑巧还能读"，一旦写入方调整字段语义，读取方会在不知情的情况下读到错误数据。
- **优先级**：P1。
- **解决标志**：跨服务的数据消费改为通过 API 或事件，或者双方对被共享字段的含义有书面约定并同步变更。

**风险 C：12 个端点被多个服务同时声明**
- **证据**：`ANY /health`、`GET /swagger/*any` 被三个服务同时声明；`GET /holidays`、`GET /leaves`、`GET /leaves/:p`、`GET /leaves/me/simple` 被 `wcp-service` 和 `wcp-service-v2` 同时声明；`GET /support/locations`、`GET /support/projects` 被 `wcp-service-v2` 和 `wcp_review_service` 同时声明。
- **影响**：这类请求到底由谁处理，取决于网关/反向代理的路由配置而非源码本身；`health`、`swagger` 这类基础设施端点重复问题不大，但 `holidays`/`leaves` 的重复意味着"改了新服务的接口，用户实际请求却打到了旧服务"这种低级但容易发生的错误。
- **优先级**：P2。
- **解决标志**：每个业务路径只由一个服务声明，或者存在一份可核对的路由分配表。

**风险 D：28 张表在不同服务中被声明为不同的列结构**
- **证据**：例如 `wcp_leave` 在 `wcp-service-v2` 中被声明 16 列，在 `wcp-service` 中被声明 13 列；`wcp_location` 在三个服务里分别被声明 3/7/2 列。
- **影响**：至少有一份表结构描述是过时或不完整的，任何依赖某个服务代码里的表结构做判断的人都可能被误导。
- **优先级**：P2。
- **解决标志**：表结构声明统一，或者明确标注哪一份是权威声明。

**风险 E：前端的 `mainApi` 基地址无法唯一绑定到一个后端服务**
- **证据**：`wcp-ui` 中名为 `mainApi` 的请求基地址，其调用同时匹配 `wcp-service`（25 次）和 `wcp_review_service`（22 次），没有明显多数，判定为"无法确定归属"。
- **影响**：这个前端基地址背后大概率是网关按路径做的分流，静态代码看不出分流规则；一旦网关路由变更，前端代码本身不会有任何提示，容易在两个后端团队之间出现"这个接口现在归谁维护"的混淆。
- **优先级**：P2。
- **解决标志**：`mainApi` 下的每个调用都能明确标注实际命中的服务，或者拆分为两个独立的基地址。

**风险 F：请假模块的异步通知调用错误被大量丢弃**
- **证据**：`wcp-service-v2` 的 `internal/handlers/leave/service.go` 中 13 处（另 `brdg_impl.go`、`approvement.go` 各 4 处）通知类调用的错误被丢弃，未记录也未重试，占全系统 51 处"丢弃错误"样本的四分之一以上。
- **影响**：请假审批流程中的通知（邮件/Slack/推送）发送失败时不会有任何记录，运营和开发都无法感知，只能靠用户投诉"没收到通知"才能发现问题。
- **优先级**：P1（影响流程可靠性和可观测性，不直接涉及资金或权限）。
- **解决标志**：这些通知调用的失败被记录到日志或触发告警，或改为有限重试。

### 9.2 缺失的业务规则 `验证`

按照"业务对象+状态 → 期望规则 → 检索校验证据 → 判定"的流程，对本报告涉及的几类高风险业务对象做了抽样验证：

- **报销金额、请假余额是否有基础校验**：✅ **命中**——报销单据存在金额必须大于 0、不超过上限、货币必须存在、同一申请不可重复报销等一整套校验（`internal/handlers/reimbursement/repr.go`、`service.go`）；请假存在"剩余假期必须大于 0""剩余小时数不能为负"的校验（`wcp-service-v2` 的 `leave/brdg_abst.go`、`wcp-service` 的 `leaveService.js`）。这两项均已有防护，不作为风险列出。
- **账单金额是否有基础校验**：✅ **命中**——`internal/handlers/management/billing.go` 中存在"手工录入金额必须大于 0""月度费用不能为 0"等多条校验。不作为风险列出。
- **删除客户前是否检查该客户名下是否存在未结清账单或进行中项目**：**未命中**——在 `clientProj/repr.go`、`clientProj/service.go`、`projectspace/client.go`、`wcp_review_service` 的 `review/client.go` 中检索到的守卫（guard）里，未发现"客户仍有未结账单/项目时禁止删除"这类校验。但 `wcp_client` 同时被 `wcp-auth` 和 `wcp-service` 写入（见 9.1 风险 A），删除客户的具体实现（`DELETE /v2/client/:client_id`）所在文件未被本次基于文本模式的守卫检索完整覆盖到，不能排除校验逻辑存在于未检索到的位置。**判定为"待确认"，而非确定的缺失**：已检查位置为上述四个文件中包含 `client` 关键字的守卫记录；未检查客户删除的完整调用链与 `wcp-service`/`wcp-auth` 侧对 `wcp_client` 的写入逻辑。

### 9.3 未使用的代码 `事实`

未发现成规模的"有完整实现但无任何入口可达"的功能模块。已发现的相关信号是：4%（19/539）的入口因动态构造等原因无法继续追踪到实现（见第 3 章"待确认"状态），这些入口本身存在，但静态分析无法确认它们是否真的连接到了可执行代码——这与"确定未使用"不同，只是"看不清"。

### 9.4 文档与代码不一致 `事实`

- `wcp-ui` 的 README 声明"antd 和 ahooks 已废弃，请勿继续使用它们，改用 bootstrap / react-hook-form / react-datepicker / react-number-format / react-select"，这是一条主动声明的技术栈迁移提示，而非文档与代码矛盾，但值得在新功能开发前提醒团队核对现状。
- `wcp-service` 的 README 描述了完整的本地 LDAP 认证搭建流程（作为用户凭证库），但当前代码库中还存在一套独立的 `wcp-auth` OAuth2 服务和 `wcp_employee_auth` 表内的 `password` 字段——README 描述的 LDAP 方案与代码中实际存在的两种认证路径（自建 OAuth2 + 本地密码）之间的关系未在文档中说明，`待确认`：是否 LDAP 已被替换、并存，还是仅用于开发环境。

### 9.5 待确认 `不可得`

- **登录是否真的支持 Google OAuth**：`wcp-auth` 中出现 `GoogleOAuth` 等命名，但静态分析工具本身对"认证注解"采用按名称匹配的方式，在认证类代码库中容易过度匹配（分析器自身局限，见第 12 章），无法确认这是否是一条真正生效的登录路径。
- **客户删除前的完整校验逻辑**：见 9.2，未检索到 `wcp-service`/`wcp-auth` 侧对 `wcp_client` 写入路径的完整校验证据。
- **北森集成的具体调用地址与数据范围**：集成本身是事实（专门的处理文件与同步任务存在），但它调用的域名/接口地址是运行时拼接的，静态代码中未出现字面量 URL，无法确认具体对接了北森的哪些接口、传输了哪些字段。
- **员工档案变更是否记入操作审计表**：`wcp_operation_record` 确认存在且被账单模块使用，但未逐一确认其余模块（如员工档案、请假状态变更）是否也写入了该表。

**所以呢**：本章列出的架构风险大多不是"代码写错了"，而是"两套服务共享数据库、缺少接口边界"这个更根本的架构选择带来的后果——`wcp-service` 到 `wcp-service-v2` 的迁移一天不完成，这些风险就会一直存在。缺失的业务规则一项检查下来，报销和请假这两个最容易出问题的资金/假期场景其实防护得不错，真正没查清楚的是客户删除这类低频但一旦发生就难以回滚的操作。

## 10. 不应做的假设

- 报告第 2 章把 `wcp-service` 列为"仍在使用"，不等于它是被优先维护和迭代的系统——它更像是尚未完成迁移的遗留服务，仍被使用不代表被积极投入。
- 报告第 3 章把某个功能标记为"有入口且可达"，不等于该功能在业务上仍然活跃或对外可见——报告只能证明代码里存在路由声明并且能顺着代码追踪下去，不能证明有真实用户在使用它。
- 第 9.2 章说"未在检索到的位置发现客户删除前的余额/项目校验"，不等于这条规则真的不存在——它也可能在未被本次检索覆盖到的代码位置、数据库约束，或者只是一条运营上的人工核对流程，从未写进代码。
- 第 7 章列出的外部依赖是从代码里检索到的字面量地址得到的，不等于系统实际对接的第三方就只有这些——运行时拼接的地址（如北森的具体接口）本报告读不到，只能说"存在这个集成"而不能说"只有这些"。
- 第 4 章的权限矩阵是抽样命中的证据，不等于列出的角色-模块对应关系是唯一或完整的授权路径——很多授权判断分散在业务代码里，静态检索一定会有遗漏。
- 第 9 章没有把某个模块列为风险，不等于它没有问题——只表示本次静态审阅没有找到证据，第 12 章说明的覆盖缺口（例如 6% 的行为覆盖率）意味着大量代码根本没有被行为分析触达。

**读取范围**：五个仓库共 2114 个文件被读取（`wcp-service-v2` 411、`wcp-ui` 1022、`wcp-service` 482、`wcp_review_service` 148、`wcp-auth` 51），另有 14 个文件被排除，总计约 19.9 MB 源码。未读取的文件类型主要是样式表、图片、字体、锁文件、环境变量文件等非逻辑代码文件（按仓库不同，各有一份不支持的扩展名清单）。

**分析器局限**（`事实`，影响本报告可信度的关键点）：
- **可达性与追踪**：47%（1944/4109）的代码入口可以被继续向下追踪；4%（19/539）的入口因动态构造等原因无法追踪；18%（93/520）的调用链在追踪过程中提前终止（多因存在循环或分支过多）；6 个路由声明了处理函数名但无法解析到具体符号。
- **行为覆盖率低**：只有 6% 的文件被至少一条行为追踪触达，3% 未能分类，其余 91% 属于"纯技术性代码"（框架样板、工具函数等）——这意味着本报告中关于"某功能如何工作"的结论集中在少数已被追踪到的路径上，大量代码本身未被行为层面分析过。
- **出站调用**：14%（66/474）的出站调用无法关联到已知路由或目标（可能是未解析的目标或调用了外部服务）。
- **表结构**：160 个数据实体读到了字段与约束详情，另有 19 张表被代码使用但没有找到对应的表结构声明，这部分表的字段信息本报告无法给出。
- **权限/校验/事务边界**：237 处事务边界、1729 处错误处理、113 处权限注解均基于文本模式匹配识别，属于"推断"而非"精确解析"，可能包含注释或字符串中的误命中，也可能遗漏用其他写法表达的同类逻辑。
- **功能分组**：65 个端点（539 个中）未被归入任何已命名的业务功能；另有 116 个词语在两个以上位置出现但规模不足以单独成为一个功能分组。
- **静态检索无法穷举权限判断**：`auth-annotation` 只能判断"是否需要登录"，具体角色判断依赖对业务代码文本的抽样检索（见第 4 章），非穷尽式解析。
- **route/组内前缀解析**：部分路由的完整路径依赖跨函数的分组前缀，若分组在多个函数或文件间传递，前缀可能不完整。

**各章节的证据充分度**：

| 章节 | 证据充分度 |
|---|---|
| 1. 项目定位 | 有证据（README + 模块结构），结论为推断 |
| 2. 系统组成 | 有证据（路由声明 + 调用统计） |
| 3. 功能地图 | 有证据，但 12% 的端点/术语未能完整归类 |
| 4. 角色权限 | 部分有证据（角色枚举为事实，权限矩阵为抽样，非穷举） |
| 5. 核心对象 | 有证据（表结构 + 状态枚举），对象间关系为低置信度推断 |
| 6. 数据流转 | 有证据（读写归属 + 隔离证据），部分为已检查未发现 |
| 7. 外部依赖 | 有证据（出站调用字面量），北森等运行时拼接的地址无法由静态源码确认 |
| 8. 运营能力 | 有证据（路由 + 校验规则） |
| 9. 风险 | 有证据（结构性发现均可追溯到具体表/端点） |

**所以呢**：本报告最大的方法论边界是"只有 6% 的代码被行为层面分析触达、权限判断依赖抽样检索"——这意味着报告里越具体的结论（比如某条金额校验、某个角色门控）越可信，因为它们直接来自代码文本；而越是"系统性归纳"的结论（比如权限矩阵的完整性、某个规则是否真的完全没有），可信度就要打折扣，需要业务方结合实际运营经验交叉验证。
